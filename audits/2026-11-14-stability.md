## Подтверждённые дефекты

### A1. Закрытое контекстное меню трека зацикливает Radix Presence

Серьёзность: **падение окна**. Это стек из сообщения.

Где:

- `src/renderer/src/widgets/track-sidebar/TrackSidebar.tsx`, `TrackMenu` (примерно строки 205–238): у каждой видимой строки свой `ContextMenu` и сразу `ContextMenuContent`.
- `src/renderer/src/components/ui/context-menu.tsx`, строки 16–23: `Content` всегда рендерит `Portal` + `Content`, даже когда меню закрыто.
- Установленный бандл `node_modules/.vite/deps/chunk-SMQAGKRA.js`, `usePresence`, строки 1370–1406. `node_modules/.vite/deps/radix-ui.js`, `MenuPortal` около строки 4612 и `MenuContent` около строки 4622: у одного меню два `Presence`.

Что происходит:

1. Меню закрыто, `present === false`, узел портала не монтируется, `node` остаётся `undefined`.
2. На mount layout-эффект всё равно вызывает `send("ANIMATION_END")` (ветка `else` на строке 1405).
3. React считает `dispatch` из `useLayoutEffect` вложенным обновлением. Лимит — 50 (`Maximum update depth exceeded`, тот же текст, что в стеке: `getRootForUpdatedFiber` → `enqueueConcurrentHookUpdate` → `dispatchReducerAction`).
4. Стартовое окно виртуального списка — `{ start: 0, end: 32 }` (`TrackSidebar.tsx`, строка 273). 32 строки × 2 `Presence` = 64 вложенных `dispatch` на первом коммите. Порог переходится примерно с 25 видимых строк.

Почему это всплыло после правок списка: контекстное меню теперь на каждой строке, а не одно на список. Пустой список не падает. Падает первый показ достаточно длинного списка и любое повторное монтирование этих строк (сортировка, фильтр окна, анимация входа).

Что проверить при починке: открыть 30+ файлов при видимом сайдбаре. Правый клик не обязателен — падение на mount закрытых меню.

Почему это именно цикл, а не «много меню за один кадр»: исключение бросает `getRootForUpdatedFiber`, когда `nestedUpdateCount` уже больше лимита. Счётчик растёт между коммитами, а стек — `commitHookEffectListMount`, то есть эффект монтируется заново, а не перезапускается. `send("ANIMATION_END")` при `node == null` на ещё не смонтированном fiber в React 19 планирует новый проход, тот снова монтирует эффект. В бандле ветка `else { send("ANIMATION_END") }` на месте; в более новых `@radix-ui/react-presence` её убрали. Пакет проекта — `radix-ui@^1.8.1`, React `^19.0.0`. Корень `src/renderer/src/main.tsx` обёрнут в `StrictMode`, он монтирует эффекты дважды и этот баг проявляет чаще.

Направление починки (не сделано): одно `ContextMenu` на список, либо не монтировать `Content`, пока меню закрыто, либо поднять `radix-ui`, где `Presence` не шлёт `ANIMATION_END` без узла. Править вендорный бандл не нужно.

### A2. `setMotion` вызывается прямо из тела рендера сайдбара

Серьёзность: **высокая**. Само по себе может не давать стек A1, но перезапускает рендер списка и заново монтирует все `Presence` из A1.

Где: `src/renderer/src/widgets/track-sidebar/TrackSidebar.tsx`, строки 485–536.

```ts
const nextPaths = visible.map((track) => track.path)
if (!motion.ready) {
  setMotion({ ... })
} else if (!samePaths(motion.paths, nextPaths)) {
  setMotion({ ... })
}
```

Это не эффект. На каждом изменении порядка путей React выбрасывает текущий рендер и начинает его заново. Внутри веток читаются `window.matchMedia`, `listRef.current` и `knownTracks` — то есть рендер зависит от DOM и от предыдущего кадра. Пока `motion.ready === false`, первый показ списка всегда делает лишний проход и только потом коммитит строки. Вместе с A1 этот проход как раз и есть момент падения.

Дополнительно: ветка `sameFiles` делает `setMotion({ ...motion, paths: nextPaths })` и тащит старый `entered`. После сортировки тех же файлов анимация «входа» может включиться повторно или не сброситься.

### A3. Подсказки тулбара рвут `asChild` у меню

Серьёзность: **средняя** (фокус, клик, второй контур Presence у dropdown). Стек пользователя — context menu, не dropdown, но тот же механизм.

Где:

- `TrackSidebar.tsx`, `ToolMenu`, строки 166–178: `Hint` оборачивает `DropdownMenuTrigger`.
- `src/renderer/src/components/ui/tooltip.tsx`, `Hint`, строки 93–99: без `pass` триггер тултипа — это `span.hint-host`, а меню оказывается внутри span.

Итог: якорь Popper — span, а не кнопка. У тултипа и у dropdown свой `Presence`. Открытие «+», сортировки или «ещё» может повторно гонять layout-эффект Presence (тот же `send` из A1), только порог 50 здесь один, поэтому само по себе реже роняет окно. Клик и клавиатура по кнопке внутри span ведут себя нестабильно.

### B1. Мультивыбор обрывает воспроизведение

Серьёзность: **средняя**. Файл на диске не портится, звук и позиция пропадают.

Где: `src/renderer/src/widgets/player/Player.tsx`, строка 161 и эффект 253–311.

```ts
const currentPath = useEditor((state) => (state.selected.length === 1 ? state.selected[0] : ''))
```

При любом выделении, кроме ровно одного пути, `currentPath` становится `''`. Эффект ставит паузу, снимает `src`, удаляет `dataset.path` и обнуляет огибающую. Позиция (`positionRef`) сбрасывается в 0. Возврат к одному треку грузит файл заново с начала.

Кнопка Play тоже выключена при `pickedCount !== 1` (около строки 613), то есть плеер сознательно привязан к одиночному выбору. Shift-клик или Ctrl-клик по списку во время прослушивания всё равно рвёт уже играющий элемент. `nowPlaying` после этого гасится эффектом на строках 471–474.

### B2. `clear()` оставляет шаблон имени, команду play и диалоги

Серьёзность: **средняя**. Кнопка «Очистить» и пункт меню зовут `clear` (`TrackSidebar.tsx` около 657, `Chrome.tsx` 116, `titlebar.tsx` 135).

Где: `store.ts`, `clear`, строки 626–642.

Сбрасываются треки, выделение, apply-поля, undo/redo, `sourceDir`, ошибки записи и прогресс. Не сбрасываются:

- `fileMask`, `fileDir`, `fileAll`, `fileNumbers`, `fileNumberSeed` — следующая порция файлов попадает под старый шаблон переименования;
- `playCommand` — плеер сам гасит `nowPlaying`, когда выбор пустой (эффект B1), но команда play в сторе остаётся;
- `savePreview`, `resetAsk`, `closeAsk` — флаги диалогов остаются поднятыми;

`nowPlaying` сам метод не трогает. Его обнуляет уже смонтированный `Player`. Если плеер в этот кадр не подписан, флаг «сейчас играет» переживает пустой список, и повторный `requestPlay` на тот же путь (строки 1131–1133) уходит в паузу вместо старта.

### B3. Обновление списка затирает несохранённые правки и может вернуть старый состав

Серьёзность: **высокая** (потеря ввода).

Где:

- `toVm`, `store.ts` 180–190: `draft` и `draftCover` всегда копируются с диска.
- `refresh`, 522–549: после `await` каждый трек заменяется на `toVm(snapshot)`. Черновик, обложка и отличие от original пропадают. В undo этот шаг не кладётся, поэтому Ctrl+Z не возвращает текст, который был на экране (в стеке только снимки *до* прошлых правок).
- Список берётся из `current`, снятого до `await`, а не из стора после await. Удаление или новое добавление, случившееся пока теги читались, затирается этой старой очередью: убранный файл возвращается, добавленный пропадает.
- `refreshSource`, 552–575: для файлов внутри `sourceDir` та же замена на `toVm`. Черновики папки пропадают.
- Кнопка обновления (`TrackSidebar.tsx` 548–563) не смотрит на `saving`. При открытой папке она ждёт `refreshSource`, затем ещё раз `refresh`. Два прохода, два окна для гонки.

`refresh` / `refreshSource` выходят сразу, только если `loading === true`. Флаг `saving` их не держит.

### B4. `addPaths` не держит загрузку, пока жив второй вызов

Серьёзность: **средняя** (гонка списка и спиннера).

Где: `store.ts` 475–505. `onTrackBatch` в `electron/preload/index.ts` 24–28 вешает слушатель на общий канал `IPC.trackBatch`. Тот же канал шлёт и `readTags` из refresh (`electron/main/index.ts` 337–340).

Два перекрывающихся `addPaths` (повторный дроп, пока первый ещё читается):

1. Оба ставят `loading: true` и оба подписаны на один канал, поэтому пачки чужого чтения тоже попадают в `accept`. Повтор по пути отсекается, дублей обычно нет.
2. `finally` первого вызова делает `set({ loading: false })`, даже если второй ещё в `await`.
3. С этого момента `refresh` больше не видит `loading` и может прочитать старый список (B3) параллельно с дописыванием второго вызова.

Отдельного счётчика или поколения загрузки нет. `openFolder` (`store.ts` 514–519) сначала пишет `sourceDir`, потом `await addPaths`. Сам диалог папки возвращает путь каталога (`electron/main/index.ts` 320–325), `readTracks` его раскрывает (`electron/services/library.ts` 62–64). Это не баг пути. Баг — общий флаг `loading`.

### B5. Каждый символ — отдельный шаг undo

Серьёзность: **средняя**.

Где: `setField` 757–777, `setFileMask` 921–924, `setFileDir` 927–930, `setFileNumber` 939–946, `setCover` 832–845. Все зовут `pushUndo` (строка 226), стек режется до 30.

Форма пишет стор на каждый `onChange` (`MetadataForm.tsx`, например 253 и 394). Длинное название или комментарий вытесняет из стека прежние осмысленные шаги и очищает redo. Отдельной склейки серии нажатий нет.

`undoOnce` / `redoOnce` (877–894) не проверяют `saving`. Проверяют только `undoTo` / `redoTo`. Меню (`use-bindings.ts` 19–20) и шорткат `redoAlt` (строки 33–36, до фильтра полей ввода) срабатывают во время записи на диск.

### B6. Завершение `saveAll` накладывает старый патч на текущий черновик и помечает поля чистыми

Серьёзность: **высокая**, если за время `await` черновик успел измениться. Само нажатие клавиш форма блокирует (`MetadataForm.tsx` 167, `disabled = saving`), но undo/redo и обновление списка — нет (B3, B5).

Где: `store.ts` 1023–1078.

`jobs` снимаются с `get()` до `writeTags`. После ответа стор обновляется так:

```ts
const original = { ...track.original, ...job.patch }
draft: { ...track.draft, ...job.patch }
```

`job` — замыкание на начало записи, `track.draft` — черновик на момент ответа. Поля из старого патча затирают более новый ввод и одновременно попадают в `original`, поэтому сравнение считает их чистыми: повторное сохранение их уже не возьмёт. Правки других полей, которых в патче не было, остаются.

Дополнительно патч — это не сырой черновик, а `writtenTags` (`shared/plan.ts` 100–112, 133–136, 181–188). В текстовых полях `%…%` раскрываются, а при активной нумерации в патч пишется `trackNumber` из номера файла, даже если пользователь номер трека не менял. После успеха эти раскрытые значения становятся и original, и draft.

Обложка: если в задании есть `cover`, `draftCover` заменяется целиком, даже когда за время записи обложку уже сменили.

### C1. Сбой или таймаут утилиты заставляет перезаписать весь пакет в основном процессе

Серьёзность: **высокая** (повтор переименования, «пропавший» файл в списке).

Где:

- `electron/main/index.ts`, `writeWithUtility` 227–259 и `writeAll` 262–283.
- `electron/main/writer.ts`, `run` 21–37: прогресс и `done` уходят только если процесс дожил до конца цикла.
- Таймаут 10 минут: `child.kill()`, промис отклоняется (`index.ts` 245–247). Ненулевой `exit` до `done` тоже отклоняет (255–256).

`writeAll` в `catch` не смотрит, сколько файлов утилита уже записала, и вызывает `writeTrack` для каждого задания заново.

Что ломается:

- Теги в том же файле повторно записать можно: `writeTrack` копирует исходник во временный файл и пишет патч ещё раз.
- Переименование — нет. Первый проход уже сделал `unlink(job.path)` (`tag-io.ts` 249–254). Второй проход зовёт `access(job.path)` и получает ошибку. В результат попадает `ok: false` без `savedPath`. Новый файл на диске есть, список по-прежнему держит старый путь, черновик остаётся грязным. Повторное «Сохранить» снова ищет уже удалённый путь.
- `kill` посреди `replaceOriginal` (`tag-io.ts` 180–196) может оставить только `.bak` или `.tmp`: исходник уже переименован в backup, а временный файл ещё не встал на место. Повтор в main этого не чинит.

Успешный `done` с пустым `results` (утилита не разобрала задания) до `saveAll` доходит как обычный ответ. Там `results.length !== ready.length` (`store.ts` 1041) бросает «Запись вернула неполный результат», черновики не помечаются чистыми. Это безопасный отказ, если на диск ещё ничего не попало. Если `done` потерялся после частичной записи, срабатывает уже ветка `exit` и полный повтор — это C1, не эта проверка длины.

Хвост, который редактор не показывал, стирается. `tags.lyrics` и `tech.lyrics` обрезаны оба; форма (`MetadataForm.tsx` 210–214) читает `draft.lyrics ?? tech.lyrics`, а `draft.lyrics` после `toVm` всегда строка, так что запасной текст не длиннее.

### C3. Замена или снятие обложки оставляет одну картинку

Где: `coverFromPictures` (`tag-io.ts` 45–54) берёт `FrontCover` или иначе первый кадр и отбрасывает остальные, в том числе пустые и больше 8 МБ. `applyPatch` 173–177: `cover === null` ставит `pictures = []`, а новая обложка ставит массив из одной передней. ### C4. Исходник не удалился после переноса — список всё равно переезжает на новый путь

Серьёзность: **средняя**.

Где: `writeTrack` 249–254 возвращает `ok: false`, `code: 'locked'`, но с `savedPath`. `saveAll` (`store.ts` 1045–1055) для неуспеха всё равно подменяет путь, если `savedPath` отличается, и не обновляет `original` / `draft`. Новый файл с тегами уже есть, старый тоже остался, строка смотрит на новый путь, черновик всё ещё грязный. Повторное сохранение пишет в новый файл ещё раз и снова пытается удалить старый путь, которого в задании уже нет.

`replaceOriginal`: если перенос исходника в `.bak` прошёл, а обратный `rename` и откат оба не удались, на целевом пути файла нет, он остаётся только под случайным именем `.bak`. Это окно гонки при убийстве процесса, не отдельная ветка успешного возврата.

### C5. «Сохранить копию» сначала затирает выбранный путь, потом пишет теги

Серьёзность: **высокая**, если в диалоге выбран уже существующий файл.

Где: `electron/main/index.ts`, `IPC.saveCopy` 384–394.

```ts
await copyFile(job.path, result.filePath)
return writeTrack({ path: result.filePath, patch: job.patch, cover: job.cover })
```

`copyFile` из `node:fs/promises` без `COPYFILE_EXCL` заменяет цель. Отдельной проверки в обработчике нет: диалог вернул путь — файл уже перезаписан сырой копией исходника. Подтверждено по коду и по поведению диалога сохранения.

Дальше `writeTrack` читает уже эту копию, патчит временный файл и делает `replaceOriginal`. Если запись падает, прежнее содержимое цели не возвращается: на диске остаётся непатченая копия. Исходный трек при этом жив.

`saveCopy` в сторе (`store.ts` 1101–1106) берёт задание только из `buildJobs`. Чистое поле кнопку до диалога не доводит: `job` нет, метод выходит. Кнопка в окне стоит у ошибки записи (`SaveBar.tsx` около 588), то есть путь обычно ещё грязный.

### Проверено в этом блоке, дефектом не считается

- Прогресс `message.current && message.total` (`index.ts` 250). Утилита шлёт `current: index + 1`, ноль не бывает. Первое сообщение не проглатывается.
- Протокол `writer.ts`: утилита читает `event.data` (`59`), запасной `worker_threads` передаёт сырое тело (`61`). `unwrap` (`40–45`) понимает и `{ jobs }`, и `{ data: { jobs } }`. Для Electron `parentPort` событие — `MessageEvent`, так что пустой `done` из-за двойной обёртки отсюда не следует. Типы Electron в `node_modules` этим проходом не открывались (`electron` в `package.json` — `^45.2.2`).
- Заблокированные задания до утилиты не доходят: `requestSave` / `saveAll` выходят, если `orderWrites(...).blocked.length` (`store.ts` 1005–1008 и 1033–1035).

## Подтверждённые дефекты (drop, список, форма, закрытие)

### F1. Папка с точкой в имени не открывается перетаскиванием

Серьёзность: **высокая** (часть библиотеки молча не попадает в список).

Где: `src/renderer/src/features/editor/lib/drop.ts`, `takeDrop` 39–56. `fileKind` умеет папку только если второй аргумент `true` (`drop.ts` 23–24), но `takeDrop` всегда зовёт `fileKind(file.name, false)`. Признак папки — `!extensionOf(file.name)`, то есть «в имени нет точки».

`Album` попадает в библиотеку. `Album.CD1`, `Artist.Album`, `Vol.1` получают расширение `.cd1` / `.album` / `.1`, это не аудио, не картинка и не `.txt`, поэтому `missedKind`. В список путь не кладётся.

Тост «Формат файла не поддерживается» (`App.tsx` 163–166) есть только когда в дропе нет ни одного принятого аудио, картинки или текста. Рядом с нормальным `.mp3` такая папка пропадает без сообщения.

Диалог «Открыть папку» это не задевает: в main уходит путь каталога, расширение имени не смотрится.

### F2. Обложка и текст из дропа садятся не на новые файлы

Серьёзность: **средняя** (правка уходит в уже открытый трек).

Где: `App.tsx` 140–156 и `addPaths` в `store.ts` 486–489.

Комментарий в `handleDrop` говорит, что картинка или txt после аудио ляжет на только что добавленное выделение. `addPaths` так не делает:

- если что-то уже выбрано, `selected` не меняется;
- если список был пуст, выбирается один первый трек без ошибки, не вся пачка.

Дроп «несколько песен + cover.jpg» при уже открытом треке пишет обложку в старое выделение. На пустом списке обложка попадает только в первый файл пачки. Остальные картинки и тексты тоже отбрасываются: берутся `images[0]` и `texts[0]`.

### F3. Обновление папки после дропа может смотреть не в ту папку

Серьёзность: **средняя** (кнопка обновления не видит часть только что добавленного, черновики внутри узкой папки затираются как в B3).

Где: `parentDir` и `sharedDir` (`store.ts` 155–162), запись `sourceDir` в `addPaths` (491). `openFolder` (514–518) сначала кладёт путь, который вернул диалог, и этот пункт его не ломает.

У дропа `sourceDir` пустой, пока не придёт первая пачка. `readTracks` сначала отдаёт файлы каталога, потом подкаталоги (`library.ts` 24–30), а первая пачка уходит сразу (`pushFile` 54, пока файлов не больше 8). Если в корне брошенной папки нет аудио, первая пачка — файлы первого подкаталога, и `sourceDir` навсегда становится этим подкаталогом. `refreshSource` читает уже его.

Отдельный край: файл прямо в корне диска, `C:\a.mp3`. `parentDir` режет по слешу и оставляет `C:` (`store.ts` 157, условие `slash > 0`). `inDir` после срезания хвостового слеша сравнивает префикс `c:/` (`store.ts` 165–169), то есть весь диск. `readTracks` для `C:` вызывает `realpath`, а это текущий каталог диска, не `C:\`. Обновление папки тогда выкидывает из списка остальные файлы диска, которых нет в этом каталоге.

### F4. Стрелки года с пустого поля ставят текущий год, с «разных» — одно число на всех

Серьёзность: **средняя** для мультивыбора (разные номера и годы становятся одним значением). Для одного пустого года — **низкая**.

Поле при этом показывает «разные», отдельного подтверждения нет. `setField` раскладывает значение на всё выделение (`store.ts` 757–776).

### F5. На инфо-вкладке пустое значение выглядит как общее

Серьёзность: **средняя** (по нескольким файлам показываются чужие BPM, тональность, путь тега).

### F6. Подтверждение закрытия во время записи убивает процесс записи

## Подтверждённые дефекты (краш, имя файла, плеер, настройки)

### G1. Второе исключение до экрана падения теряется, а чужой reject подменяет всё окно

Серьёзность: **высокая** (после плохого сочетания клавиш окно падает на каждом запуске).

Где: `src/renderer/src/app/CrashScreen.tsx`.

`installCrashHooks` вызывается только из `componentDidMount` (94–97). До этого слушателей `error` и `unhandledrejection` нет, массив `waiting` пуст. Исключение до монтирования границы (в том числе отказ промиса titlebar в preload) в очередь не попадает и на экране не появляется.

Пока `publish === null`, `remember` кладёт ошибку в `waiting` (61–66). На монтировании забирается только `waiting.shift()` (99–100). Вторая и следующие остаются в модульном массиве навсегда: их не показывают и не очищают. `publish` (96–98) пишет в state только если `state.info` ещё пуст, поэтому экран падения держит первую ошибку и молча выбрасывает следующие. В отчёт уходит только она.

`componentWillUnmount` обнуляет `publish` и не снимает слушатели (`__mteCrash` уже выставлен, 68–71). После размонтирования новые ошибки снова копятся в `waiting`. Следующее монтирование покажет одну старую, не обязательно ту, что случилась сейчас.

`describeError` (9–17) понимает `Error` и строку. `reject(404)`, `reject(null)` и обычный объект дают пустые `message` и `stack`, и `remember` их выбрасывает (63).

Связка с настройками, из-за которой это не теоретический край:

- `setShortcut` сохраняет сочетание в `localStorage` и сразу шлёт четыре нативных акселератора (`prefs.ts` 102–117 и 169–177).
- В main уходят только open, save, undo, redo. Проверка — `ACCELERATOR` в `validate.ts` 78 и `assertAccelerator` 106–109. Запятая, Tab, пробел, стрелки влево и вправо, символ вроде `!` (Shift+1) не проходят.
- `App.tsx` 59–61 на каждом запуске вызывает `syncShortcuts`. Отклонение промиса никто не ловит (`prefs.ts` 117 и 250).
- `CrashBoundary` уже смонтирован, `unhandledrejection` поднимает экран падения вместо редактора. Перезагрузка читает тот же `localStorage` и падает снова.

Клавиши по умолчанию для этих четырёх пунктов (`Ctrl+O/S/Z/Y`) проверку проходят. Достаточно переназначить «Сохранить» на `Ctrl+,` или `Ctrl+Shift+1`.

`setAppSettings` (`app-settings.ts` 41) и `setLocale` (`i18n.ts` 82) тоже без `catch`. Ошибка записи настроек идёт тем же путём в полный экран. `applyLiveSettings` для пункта автозапуска ошибку глотает (`electron/main/index.ts` 56–61) и всё равно возвращает уже записанный флаг: переключатель «при входе в систему» может гореть, хотя вызов системы не удался.

### G2. Имя устройства Windows проходит в путь записи

Серьёзность: **высокая** на Windows, если маска или поле даёт такое имя.

Где:

- `sanitizeFileStem` (`shared/filename.ts` 76–82) выкидывает символы `<>:"/\|?*` и точки по краям. `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` остаются. Регистр не важен: после обрезки `con.` это по-прежнему `con`.
- `applyMask` (137–143) подставляет этот stem. `resolveTarget` (151–163) склеивает каталог и `${stem}${ext}`.
- `assertWriteJob` (`validate.ts` 169–170) проверяет у нового пути только строку и расширение аудио. `CON.mp3` проходит.

На Windows имя без учёта расширения зарезервировано за устройством. `copyFile` / `rename` в `writeTrack` (`tag-io.ts` 240 и 180–191) идут на этот путь. Сам вызов `copyFile('…', 'CON.mp3')` в этом заходе не запускался: дефект — пропуск фильтра и проверки, не измеренный код возврата системы.

Длина stem тоже не ограничена. Имя длиннее лимита компонента Windows упирается уже в ошибку `rename`, отдельным ранним отказом это не ловится.

### G3. Ошибка чтения `media:` после ответа клиенту уже не 404

Серьёзность: **средняя** (воспроизведение обрывается, процесс из этого файла не падает).

Где: `electron/main/media.ts` 43–75.

`try/catch` закрывает только путь до `return new Response`. `createReadStream` создаётся на строке 70, тело отдаётся как `Readable.toWeb(node)`. Ошибка чтения (файл удалён или заменён записью, диапазон уже не сходится с размером из `stat`) случается после отправки статуса 200 или 206. В 404 это не превращается.

В `media.ts` нет своего `node.on('error')` и нет подписки на `request.signal`. Подписчик `error` у потока Node ставит `Readable.toWeb`, поэтому необработанное событие `error` из этого файла не следует. Обрыв запроса доигрывает отмена веб-потока, если её сделает потребитель. Утечку дескриптора при перемотке этим заходом не гоняли.

Плеер на `error` аудио ставит паузу и тост, кроме `MEDIA_ERR_ABORTED` (`Player.tsx` 418–424). Повторно тот же путь не открывает (`failedRef`).

### G4. Закрытые popover основной вкладки снижают порог падения A1 примерно на шесть строк

Серьёзность: **высокая** вместе с A1. Сами шесть штук лимит 50 не выбирают.

Где: `fields.tsx` 81–128 (исполнитель, жанр, альбом, исполнитель альбома — четыре `combo` в `MetadataForm.tsx` 259, 269, 289, 299) и два popover undo/redo в `SaveBar.tsx` 236–271.

Каждый закрытый popover, как контекстное меню в A1, всегда держит в дереве `Portal` и `Content`. По коэффициенту A1 это 2 Presence на меню. Шесть меню — 12 Presence, около шести видимых строк списка. Порог A1 «примерно 25 строк» на основной вкладке сдвигается к примерно 19, если других новых Presence в этом кадре нет.

Пустой список эти popover не монтирует: форма появляется только при `hasTracks` (`App.tsx` 196–201). Поэтому пустое окно не падает, а первый показ длинного списка совпадает с появлением этих шести меню.

Режим меню по умолчанию — `icon` (`shared/types.ts` 186). В titlebar тогда один `MenubarContent` (`titlebar.tsx` 208–224). Пять `MenubarSubContent` лежат детьми этого контента. Если закрытый Presence не монтирует детей, они в порог не входят; если монтирует, это ещё 10 Presence и порог падает сильнее. Бандл `usePresence` в этом заходе не открывался, вторую ветку не перепроверял.

`Hint` и закрытые `Dialog` (настройки, три диалога записи, палитра, обложка) есть и на пустом окне. Пустой список не падает, значит они не добирают 50 сами. Их вклад в порог вместе со строками этим заходом не измерялся.

## Подтверждённые дефекты (палитра, копирование, факты, прокрутка)

### H1. Копирование файлов кладёт весь список в командную строку PowerShell

Серьёзность: **средняя** (большая пачка не копируется, файлы на диске не портятся).

Где:

- `electron/services/clipboard.ts`, `copyFileList` 33–48. На Windows пути сериализуются в JSON, кодируются в base64 и подставляются в аргумент `-Command` у `powershell.exe`.
- `electron/services/validate.ts`, `assertPathList` 72–75: до `MAX_FILES` (5000) путей. `assertDragFiles` 112–121 перед копированием синхронно делает `statSync` на каждый путь в основном процессе.

Лимит командной строки Windows — 32767 символов. Base64 длиннее JSON примерно на треть. Несколько сотен длинных путей уже не влезают, полная пачка из лимита — тем более. `execFile` падает, рендерер показывает «Не удалось скопировать файл» (`copy.ts` 29). Буфер обмена не меняется.

До этого `statSync` по тысячам путей блокирует main: окно не обрабатывает запись, закрытие и плеер, пока проверка не кончится. Отдельного потолка на длину команды нет, временный файл со списком не используется.

Не-Windows ветка (36–38) пишет в буфер текст путей, а не файловый drop. Сборка смотрит в первую очередь на Windows; на других платформах «Копировать файлы» молча кладёт текст.

### H2. Второе копирование, пока первое не вернулось, пропадает без сообщения

Серьёзность: **низкая**.

Где: `src/renderer/src/features/editor/lib/copy.ts` 3, 19 и 38. Модульный `busy` общий для `copyTracks` и `copyPlain`.

Повторный Ctrl+C в сайдбаре (`use-bindings.ts` 48–51), второй пункт меню или копирование пути, пока PowerShell ещё жив, выходит сразу. Тост не показывается. `finally` снимает флаг только у первого вызова. Зависший PowerShell (H1, процесса без таймаута) оставляет `busy` до конца этого процесса, очередь в main при этом отдельная (`clipboard.ts` 20–26) и до неё второй вызов уже не доходит.

Тосты `copyTracks` зашиты по-русски (25–30) и не идут через `tr` / пакет локали. При английском интерфейсе удачное и неудачное копирование файлов и путей из сайдбара всё равно на русском. `copyPlain` тексты получает снаружи, там пакет уже используется.

### H3. Home и End на разделителе сайдбара ещё и меняют выделенный трек

Серьёзность: **низкая**.

Где:

- `use-bindings.ts` 59–62: обработчик `window` на Home/End вызывает `selectEdge` и не смотрит `defaultPrevented`. Ранний выход есть только для input, textarea, select, contenteditable и `[data-no-track-nav]` / `[role="menu"]`. У разделителя `role="separator"`.

Фокус на разделителе (он в tab-порядке, пока сайдбар открыт) и Home одновременно сжимают колонку и выделяют первый трек. End — расширяют и выделяют последний. Стрелки влево и вправо до списка не доходят: их обрабатывает только разделитель.

`setSidebar` из `useState` стабилен (`App.tsx` 55). Эффект ширины (359–364) пишет в стор только если значение вне 220–350. Цикла нет. Ширина пишется в `localStorage` отдельным эффектом (`App.tsx` 73–75).

### H4. Поиск по палитре на каждом символе прогоняет весь список и сразу монтирует десятки обложек

### H7. Отпущенный захват ползунка прокрутки больше не прячет полосу

Серьёзность: **низкая**.
